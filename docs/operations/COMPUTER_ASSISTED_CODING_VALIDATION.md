## Implemented outcome

The application can validate and activate immutable ICD-10 2010 and ICD-9-CM 2010 workbook releases, search the active catalogs, generate bounded explainable ICD-10 candidates from an exact approved clinician-authored diagnosis, generate separate ICD-9-CM candidates from an exact completed performed-procedure record, and preserve both decision chains. Candidate generation never creates a code assignment. A coder must explicitly accept a candidate or select a source-matched manual alternative, submit the immutable draft, and obtain approval from the exact linked RMIK supervisor. Finalization requires separate approved assignments for every current diagnosis and every current performed procedure.

The interface permanently labels the feature `Wajib ditinjau koder` and `Bukan finalisasi otomatis`. Retrieval scores are not presented as clinical probabilities, and no bulk-accept action exists.

When a coder requests documentation correction, the reference implementation creates an exact medical-author task, blocks coding, requires an immutable medical successor and linked supervisor approval, invalidates older code assignments as `REVIEW_REQUIRED`, requires an approved successor closure, and treats the old RMIK approval as stale until a replacement RMIK review is approved. Orders, prescriptions, and the original clinical occurrence time are locked in this correction route. The blocked coder task retains and opens the exact disputed diagnosis source.

When the requested source is a performed procedure, a separate guarded lifecycle routes the request to the exact active closure/procedure author. The successor closure may change only performed-procedure documentation; other authored closure fields and the original clinical occurrence time remain locked. The exact linked medical supervisor and the prior RMIK reviewer/supervisor chain must approve the successors before coding reopens. The old procedure, closure, hashes, decisions, and assignments remain historical. The blocked coder task retains and opens that exact procedure, so the workspace defaults to ICD-9-CM rather than the first diagnosis.

Encounter closure requires an explicit `NONE_PERFORMED` or `PROCEDURES_RECORDED` attestation. A recorded procedure has completed status, clinician-authored text, performed time, performer, optional exact diagnosis/order links, and an immutable source hash inside the supervised closure. It remains separate from both the originating ServiceRequest and its later ICD-9-CM assignment. Closure replacement makes assignments tied to the old procedure source `REVIEW_REQUIRED`.

A versioned synthetic retrieval evaluator now binds the exact active release versions, row counts, and hashes before running any case. The draft baseline reports diagnosis and procedure top-1/top-5 separately, proves negative-control and ambiguity behavior, performs no clinical write, and excludes all pending Indonesian/stress proposals from reference metrics. See the [Synthetic Coding Retrieval Baseline](CODING_GOLD_SET_BASELINE.md).

## Safety properties demonstrated

- Coding endpoints cannot create or edit a diagnosis or performed-procedure source.
- Diagnosis suggestions require the current approved medical source and active ICD-10 release; procedure suggestions require a completed record from the exact approved current closure and active ICD-9-CM release. Both require the current approved RMIK review, active simulation session, and exact case assignment.
- A diagnosis run cannot use ICD-9-CM and a procedure run cannot use ICD-10; cross-system manual alternatives are rejected before assignment creation.
- A suggestion run and every candidate preserve the source-version hash, terminology-release hash, engine version, configuration hash, evidence, rank, and requesting assignment.
- Exact and no-reliable-candidate outcomes are both represented honestly.
- Rejection and correction-request decisions create no assignment.
- A correction request is bound to the exact coder, medical author, diagnosis statement/version/hash, and approved RMIK review.
- A procedure correction is separately bound to the exact coder, completed procedure/hash, closure/hash, active closure author, and approved RMIK review; it cannot enter diagnosis authoring.
- The blocked coder work task retains the exact source public ID; queue navigation and correction-aware workspace fallback open the disputed diagnosis or performed procedure instead of an unrelated first source.
- Coding remains blocked through medical amendment, closure replacement, and successor RMIK approval.
- A coding correction cannot alter service requests, prescriptions, or the original clinical occurrence time.
- A procedure correction cannot alter non-procedure closure fields or the original clinical occurrence time.
- Medical-source replacement invalidates older diagnosis assignments; closure replacement invalidates assignments tied to older procedure rows. Both become `REVIEW_REQUIRED`, while prior versions, approvals, suggestions, and decisions remain immutable.
- Manual selection is stored as `MANUAL`, not attributed to the engine.
- Superseded-release suggestion runs cannot receive a new decision.
- A draft remains non-final until the exact coder submits it and the linked RMIK supervisor approves the exact content hash.
- A nursing supervisor and users without `coding.write` are denied at the server.
- All current diagnoses and all current completed procedures must have separate approved human-created assignments before encounter finalization; `NONE_PERFORMED` creates no artificial procedure-coding requirement.
- Releases, concepts, runs, candidates, decisions, assignments, review actions, and audit events are append-only or lifecycle-guarded.

## Open validation and implementation gaps

These items must not be reported as complete:

1. **Procedure-source correction policy validation:** the dedicated route, immutable successor, scope lock, medical supervision, RMIK reapproval, and stale-source invalidation are implemented and automated. RMIK and medicine must still validate the local responsibility and timing policy before faculty UAT.
2. **Indonesian retrieval content:** the catalog displays are primarily English. Versioned aliases are supported by the data/search model, but no Indonesian synonym set is approved. Eleven proposed stress/Indonesian cases are versioned and excluded from reference metrics; eight currently expose retrieval gaps. RMIK and medicine must validate, revise, or reject mappings before any alias is enabled.
3. **Gold-set expert validation:** the executable draft set and separate diagnosis/procedure top-1/top-5 baseline are implemented. No accuracy threshold has been invented. RMIK/medicine review, accepted case labels, an approved threshold, and a version promoted from draft remain required for Checkpoint 2.
4. **Denied-action audit:** authenticated direct requests that resolve to a 403 now create one append-only `authorization.denied` event containing only actor, named route, method, status, generic reason, server time, and request correlation. Request/query/form content, exception text, IP fingerprints, and browser strings are excluded. Guest authentication redirects are not recorded as authorization denials.
5. **Browser/manual evidence:** login and the RMIK work queue passed the supported desktop/narrow baseline. Separate diagnosis and procedure correction fixtures passed exact-source navigation, edit scope, blocking, successor approvals, replacement RMIK review, human ICD-10/ICD-9-CM review, resolution, and finalization while retaining exact second-level timestamps. A later single retained browser tab/session repeated both complete branches across fresh isolated fixtures and ended with an empty retained warning/error console log; the procedure successor preserved `22:44:06–22:54:06`. Automated coverage guards the complete seven-control sign-in Tab order, error associations, and an axe-clean validation state. Full-page native keyboard traversal remains pending; automated coverage and the retained console pass do not replace that gate.
6. **External use:** no production claim, INA-CBG/IDRG grouper, SATUSEHAT submission, real-patient use, catalog redistribution, or clinical-validity claim is authorized.
